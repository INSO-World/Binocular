# MSR Ontology Gap Analysis

**Date:** 2026-04-05
**Scope:** Holistic software project analysis capability assessment
**Status:** Critical gaps identified

---

## Executive Summary

The MSR ontology successfully covers **tool integration and event tracking** (VCS, ITS, CI systems). However, it falls significantly short of supporting **holistic project analysis**. The ontology maps *what happened* (commits, issues, builds) but provides no visibility into *what matters* (code quality, architectural health, knowledge distribution, risk).

**Current State:** 40% complete for holistic analysis
**Verdict:** Rename scope or extend substantially. Current trajectory leads to expensive infrastructure with moderate analytical insights.

---

## What the Ontology Covers ✓

- ✓ Tool infrastructure (Git, SVN, Hg, Jj; GitHub, GitLab, Bitbucket, Jira, Linear; GitHub Actions, GitLab CI, Jenkins)
- ✓ Project coordination (issues, pull requests, build runs)
- ✓ Contributor tracking (basic identity, activity)
- ✓ Temporal events (commits, comments, pipeline runs)
- ✓ Multi-forge support with system-specific subclasses

**Assessment:** Well-designed for what it covers. Clean architecture, proper use of inheritance, good comment documentation.

## Critical Gaps for Holistic Analysis

### 1. CODE STRUCTURE & QUALITY (CRITICAL)

**What's Missing:**
- Module/package hierarchy (no "what code belongs to what")
- Function/class/method definitions (no code entity graph)
- Cyclomatic complexity, lines of code, code metrics
- Code smell detection or quality markers
- Test coverage mapping (which tests cover which code)
- Code ownership (who understands/maintains what)

**Why It Matters:**
Without code structure, you can see "commit happened" but not "what code changed matters." You can track issues but cannot correlate "which code areas are most problematic." There is **no way** to detect:
- Technical debt hotspots
- Architectural drift
- Over-complex modules
- Untested code areas
- Refactoring impact

**Real Impact:**
- Can't identify which modules need attention
- Can't assess refactoring ROI
- Can't measure code health trends
- Can't see if new team members understand critical code

**Example:** A project merged 500 commits this month. Five of them rewrote a core authentication module. Your ontology treats all 500 identically.

---

### 2. DEPENDENCIES & ARCHITECTURE (CRITICAL)

**What's Missing:**
- Module-to-module dependencies
- Package/library dependencies (npm, pip, Maven, etc.)
- Dependency versions and vulnerability data (CVEs)
- Circular dependency detection
- Architecture layers (presentation, business, data)
- Service boundaries, microservice definitions

**Why It Matters:**
"Holistic analysis" requires understanding the system's shape. Without dependency graphs, you're analyzing in isolation. You cannot see:
- Risk of code changes (what breaks if X changes?)
- Bottlenecks (heavily depended-on code)
- Breaking changes hidden in PRs
- Why builds fail due to dependency issues
- Architectural coupling problems

**Real Impact:**
- Can't assess architectural health
- Can't predict blast radius of changes
- Can't identify "God modules" or tight coupling
- Missing dependency risk tracking (outdated/vulnerable libraries)
- Can't validate architectural decisions

**Example:** A PR changes a utility module. Is it depended on by 2 other modules or 20? Your ontology can't tell you.

---

### 3. DEVELOPER EXPERTISE & KNOWLEDGE DISTRIBUTION (HIGH PRIORITY)

**What's Missing:**
- Code ownership (WHO understands/maintains WHAT code areas)
- Bus factor (single points of failure in knowledge)
- Expertise depth (who's a generalist vs. specialist vs. bottleneck)
- Knowledge transfer signals (mentoring, pairing)
- Reviewer expertise (not just "reviews happened" but quality/depth)
- Onboarding effectiveness

**Why It Matters:**
Project health is directly tied to knowledge distribution. Single-person dependencies destroy teams. You have contributor data but **zero visibility** into whether knowledge is concentrated or distributed.

The difference between:
- "Alice reviewed 80% of backend PRs" (bottleneck)
- "Alice reviews 20% of backend PRs and mentors juniors on each" (healthy)

...cannot be expressed or analyzed.

**Real Impact:**
- Can't identify key-person risk
- Can't measure team resilience
- Missing onboarding friction signals
- Can't optimize code review assignments
- No data on approval process bottlenecks
- Can't detect knowledge silos

**Example:** Developer leaves company. Your ontology records "contributor removed." It doesn't tell you that 60% of critical path code had only that person reviewing it.

---

### 4. REQUIREMENTS TRACEABILITY (HIGH PRIORITY)

**What's Missing:**
- Requirement → Issue → Code → Test mapping
- Feature flags and their scope
- User stories with acceptance criteria tracking
- Requirements change impact
- Specification artifacts (design docs, ADRs)

**Why It Matters:**
Without traceability, you cannot answer fundamental questions:
- "What features did we actually ship?"
- "Why was that code changed?"
- "Which requirements were incomplete?"
- "What was the scope creep?"

You track work items but lose the thread back to actual user value or business requirements.

**Real Impact:**
- Can't validate requirement completion
- Can't track scope creep
- Missing context for code reviews
- Can't measure delivery predictability
- Can't correlate features to code areas

**Example:** Issue #247 is "closed." Does that mean the feature shipped? Is it in production? Partially complete? Your ontology doesn't know.

---

### 5. QUALITY & TESTING STRATEGY (MEDIUM PRIORITY)

**What's Missing:**
- Test coverage metrics by module/package
- Test hierarchy (unit/integration/e2e relationships)
- Test flakiness tracking
- Code review comment quality/depth
- Static analysis results, linting issues
- Security scan findings

**Why It Matters:**
`TestResult` exists in your ontology but it's **hollow**—just a pass/fail. Without knowing WHAT was tested, you can't assess quality. High green builds could hide untested code.

**Real Impact:**
- Can't measure real quality risk
- Missing quality trend analysis
- Can't identify flaky tests (masks real issues)
- No visibility into code review thoroughness
- Can't correlate test coverage to risky code areas

**Example:** Build succeeded. Does that mean the critical path is covered? Untested? Your ontology can't tell.

---

### 6. DEPLOYMENT & RUNTIME METRICS (MEDIUM PRIORITY)

**What's Missing:**
- Deployment targets/environments
- Rollback events and failure recovery
- Incident/outage data
- Performance metrics (latency, throughput, error rates)
- Production vs. staging separation
- Release notes, changelog artifacts

**Why It Matters:**
Your ontology ends at "build passed." It says nothing about:
- What got deployed where
- Did it work in production?
- What broke?
- How long before recovery?

You're capturing development history but missing the feedback loop from production.

**Real Impact:**
- Can't correlate commits to production issues
- No deployment health metrics
- Can't assess release quality
- Missing feedback loop from runtime to development
- Can't measure MTTR or incident severity

**Example:** Commit shipped Monday. Service degraded Thursday. Your ontology has no connection between them.

---

### 7. EVOLUTION & CHURN PATTERNS (MEDIUM PRIORITY)

**What's Missing:**
- Code churn tracking (how often files change)
- Stability metrics (commit frequency trends)
- Architecture evolution (how structure changes over time)
- Refactoring vs. feature vs. bug fix breakdown
- Technical debt accumulation signals
- Code deletion/cleanup tracking

**Why It Matters:**
You can see individual commits but not **patterns**. High churn in core areas is a health signal. Increasing test-to-code ratio differs fundamentally from constant rewrites.

**Real Impact:**
- Can't identify problem areas needing stabilization
- Missing refactoring ROI tracking
- No early warning for architecture problems
- Can't measure code quality trends
- Can't detect "death spiral" modules (constant fixes)

**Example:** A module has been touched by 40 commits in 2 months. Is it under active development (good) or fire-fighting (bad)? Your ontology doesn't distinguish.

---

### 8. GOVERNANCE & DECISION-MAKING (LOWER PRIORITY)

**What's Missing:**
- Decision records (ADRs, design documents)
- Approval workflow duration and bottlenecks
- Stakeholder roles (beyond "contributor")
- Code ownership policies

**Why It Matters:**
Process matters. Slow reviews, unclear ownership, and conflicting decisions all damage velocity.

**Real Impact:**
- Can't identify approval process bottlenecks
- Missing process efficiency metrics
- No visibility into decision quality over time

## What This Reveals: The Strategic Problem

### You Built a Tool Integration Ontology, Not a Project Analysis Ontology

**Your ontology answers:** "What events happened in GitHub, Jira, and Jenkins?"

**Holistic analysis requires:** "Is this project healthy? Where are the risks? What should we fix?"

You conflated the two. That's the fundamental mismatch.

### You're One Layer Too High AND Too Low

**Too high:** You treat code as a black box. "A commit happened" tells you nothing about code quality, risk, or architectural impact.

**Too low:** You're mapping tool-specific fields (GitHub issue priority, Jira components) instead of building a unified semantic model that works across tools.

**Consequence:** Your ontology is **brittle**:
- If a team switches from Jira to Linear, half your analysis breaks
- If someone adds a new CI tool, you extend the ontology again
- You're building a mapping layer, not an analytical foundation

### What You're Avoiding

Looking at what's missing, I see deliberate avoidance patterns:

1. **Code structure is hard to normalize.** Python packages ≠ Go modules ≠ Java classes. You punted entirely.

2. **Dependencies require language-specific parsers.** Easier to ignore than handle 15 languages.

3. **Expert knowledge is fuzzy.** Can't pull it from git like commits. Requires inference or external data.

4. **Production metrics come from observability systems**, not development tools. You stopped at the CI boundary.

All valid challenges. **But you didn't acknowledge them—you skipped the whole section.** That's different from a deliberate design choice.

## Brutal Prioritization: What You Actually Need

If you're serious about "holistic," here's what matters in order of impact:

### Tier 1: Do These First (Enables 80% of Insights)

#### 1. Code Structure + Code Ownership Mapping
**Why:** Without knowing what code areas exist and who owns them, everything else is noise.

**What to add:**
- Package/module definitions (language-agnostic)
- File hierarchy with ownership
- Code entity graph (classes, functions if available)
- Module health indicators

**Effort:** Medium. **ROI:** Very high.

#### 2. Dependencies (Internal + External)
**Why:** Blast radius of changes, architectural risk, security exposure.

**What to add:**
- Internal module dependencies
- External package dependencies with versions
- Vulnerability/CVE mapping
- Circular dependency detection
- Architecture layer definitions

**Effort:** High. Start with one language. **ROI:** Very high.

#### 3. File-to-Issue Traceability
**Why:** Connects work tracking to actual code.

**What to add:**
- Commit-to-issue linking (PR closes issue #X)
- File changes per commit
- Issue → code → test mapping

**Effort:** Medium. **ROI:** High.

### Tier 2: Multiplies Value of Tier 1

#### 4. Code Metrics
**Why:** Identifies problem areas (complexity, coverage, churn).

**What to add:**
- Per-module: cyclomatic complexity, LOC, test coverage %
- Churn indicators (commit frequency per file)
- Code smell markers

**Effort:** Medium. Needs static analysis tooling. **ROI:** High.

#### 5. Team Expertise Distribution
**Why:** Identifies knowledge bottlenecks and bus factor risk.

**What to add:**
- Code ownership inferred from commit/review history
- Expertise depth signals (specialist vs. generalist)
- Knowledge concentration metrics

**Effort:** Low. Computable from existing data. **ROI:** High.

#### 6. Deployment & Runtime Link
**Why:** Closes the feedback loop. Distinguishes useless builds from impactful ones.

**What to add:**
- Deployment records (what → where → when)
- Build-to-production lineage
- Incident/outage correlation
- Performance metrics per deployment

**Effort:** High. Requires production telemetry. **ROI:** High.

### Tier 3: Nice to Have

- Requirements traceability (ADRs, design docs)
- Test hierarchy & coverage mapping
- Review quality metrics
- Governance workflows
- Release notes, changelog artifacts

## Path Forward: Two Options

### Option A: Pragmatic (Recommended if resources are constrained)

**Acknowledge what this ontology actually is:** A tool event schema.

It's good for:
- Building audit logs of what happened
- Correlating events across tools
- Feeding data into external analysis engines

**Label it honestly.** Don't claim holistic analysis capability. Ship the current ontology as:
- "MSR Event Correlation Schema"
- Document its scope clearly
- Market it for what it does well (multi-tool event integration)

**Effort:** Rename and document. 1 week.

**Result:** Useful but limited. Won't answer strategic questions.

---

### Option B: Ambitious (Recommended if this is core to Binocular's value)

Extend the ontology properly to support holistic analysis.

**Phase 1 (Critical):**
1. Add code structure layer (packages, modules, ownership)
2. Add dependency layer (internal + external)
3. Add file-to-issue traceability

**Phase 2 (High value):**
4. Add code metrics (complexity, coverage, churn)
5. Add team expertise mapping
6. Add deployment linking

**Phase 3 (Nice to have):**
7. Add requirements traceability
8. Add test hierarchy
9. Add governance workflows

**Effort:** 8-12 weeks for Phases 1-2. **ROI:** Very high. This becomes genuinely useful.

**Result:** A real project analysis platform, not just a tool aggregator.

---

## Recommendation

**Be honest about scope first.** What is Binocular actually trying to do?

### If the goal is:
> "Correlate events from multiple development tools into a unified view"

Then you're done. Extend your CI layer a bit, ship it. Current ontology is 90% there.

### If the goal is:
> "Understand project health, identify risks, and guide improvement decisions"

Then you're not close. **Reframe around code analysis + team dynamics, not tool events.**

Current trajectory leads to **expensive infrastructure for moderate insights**. You need code-centric analysis, not tool-centric events.

---

## Conclusion

Your ontology is well-built for its actual scope but massively under-scoped for the claims around it. The gap isn't in execution—it's in ambition and honesty about what you're building.

**Make a choice:**
1. Ship a tool aggregator and own that limitation
2. Invest in extending it into real holistic analysis

Either is fine. But don't drift between them.
